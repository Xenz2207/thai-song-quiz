# ส่วน A — ข้อมูลโปรเจกต์

| หัวข้อ | รายละเอียด |
| --- | --- |
| ชื่อและรหัสนักศึกษา | [กรอกชื่อ–นามสกุล] / [กรอกรหัสนักศึกษา] |
| ชื่อแอป | คำใบ้ทายเพลงฮิต |
| ผู้ใช้เป้าหมาย | ผู้ที่ชอบเพลงไทยและต้องการเล่นทายเพลงด้วยตนเองหรือร่วมกับเพื่อน |
| เครื่องมือ AI | Codex; ใบงานแนะนำ Google AI Studio แต่โปรเจกต์นี้ไม่ได้ใช้ Build mode ของเครื่องมือนั้น |
| เทคโนโลยีแอป | HTML, CSS และ JavaScript ใน index.html ไฟล์เดียว ไม่มี backend, login หรือฐานข้อมูลเซิร์ฟเวอร์ |

## แอปนี้ทำอะไร — 5 บรรทัด

1. เป็นเกมทายเพลงไทยจากเพลง 200 รายการที่คัดจากศิลปินต้นฉบับ พร้อมแสดงยุคและปีที่ออก

2. ผู้เล่นเปิดป้ายคำใบ้ 4 แบบหรือฟังเสียงตัวอย่างประมาณ 30 วินาทีภายในหน้าเว็บ

3. แต่ละรอบเริ่มที่ 100 คะแนน เปิดคำใบ้หัก 10 คะแนนต่อป้าย และฟังเสียงสำเร็จหัก 20 คะแนนครั้งเดียว

4. ผู้เล่นเดาในใจแล้วกดดูเฉลย ระบบแสดงคำตอบ คะแนน และบันทึกประวัติเรียงจากรอบล่าสุด

5. สุ่มเพลงไม่ซ้ำจนหมดชุด รองรับหน้าจอมือถือ และเปลี่ยนเพลงเมื่อแหล่งเสียงใช้ไม่ได้

## แนวคิดก่อนเริ่มสั่ง AI

เริ่มจากเกมโชว์ทายเพลงที่ใช้คำใบ้เป็นตัวแลกคะแนน เป้าหมายคือทำเกมในไฟล์เดียวซึ่งเปิดในเบราว์เซอร์ได้ โครงร่างหน้าจอวางคะแนนไว้ด้านบน ปุ่มฟังเสียง ถัดลงมาเป็นป้าย 2×2 และพื้นที่จบรอบด้านล่าง จากนั้นระหว่างพัฒนาเปลี่ยนวิธีตอบจากการพิมพ์เป็นเปิดเฉลย เพื่อให้เล่นแบบเดาด้วยตนเองได้ง่ายขึ้น

คะแนนในเวอร์ชันสุดท้ายเป็นคะแนนที่เหลือจากการใช้คำใบ้ ไม่ใช่คะแนนที่ระบบตรวจว่าผู้เล่นตอบถูก เพราะไม่มีช่องรับคำตอบแล้ว ผู้เล่นสามารถกดเฉลยทันทีและได้ 100 คะแนนได้ตามกติกาปัจจุบัน

## ขอบเขตที่ตรงกับใบงาน

| ข้อกำหนด | หลักฐานในแอปปัจจุบัน |
| --- | --- |
| แอปหน้าเดียว | HTML/CSS/JavaScript รวมใน index.html ไม่มีระบบหลาย route |
| โต้ตอบอย่างน้อย 3 อย่าง | เปิดคำใบ้; เล่น/หยุด/ฟังต่อ; ดูเฉลย; เล่นเพลงต่อไป; กู้คืนคลังเพลง |
| State เปลี่ยนแปลงได้ | คะแนน รอบ เพลงปัจจุบัน ป้ายที่เปิด สถานะเสียง และ playHistory |
| Responsive | Grid 2×2 และปรับเป็นคอลัมน์เดียวในหน้าจอแคบมาก; ตรวจ viewport 390×844 |
| คำอธิบายอยู่ในหน้า | มีวิธีเล่น กติกาคะแนน และการจัดการเพลงไม่พร้อม |
| ไม่มีระบบที่ไม่จำเป็น | ไม่มี login, payment, backend หรือ API key ในแอป |

## เครื่องมือที่ใช้ระหว่างทำงาน

ใช้ PowerShell และ Node.js สำหรับอ่าน/จัดข้อมูลเพลง ใช้ iTunes Search API ฝั่งประเทศไทยเพื่อค้นข้อมูลและ URL พรีวิว และใช้ Playwright ควบคุม Microsoft Edge แบบ headless เพื่อตรวจการเล่นและการโต้ตอบ เครื่องมือเหล่านี้เป็นเครื่องมือเตรียมข้อมูล/ทดสอบ ผู้เล่นไม่ต้องติดตั้งเพื่อเปิด index.html

หน้าตาใช้ CSS ที่เขียนเองและฟอนต์ Kanit จาก Google Fonts ไม่ได้ใช้ Tailwind แม้บาง Prompt จะกล่าวถึง Tailwind แอปยังทำงานได้ด้วยฟอนต์สำรองหากโหลดฟอนต์ภายนอกไม่ได้ ส่วนการฟังเสียงต้องมีอินเทอร์เน็ต

# ส่วน B — Prompt แรก

## B.1 Prompt แรกฉบับเต็ม

ข้อความต่อไปนี้คัดจากคำขอแรกของผู้ใช้ โดยคงข้อความและลำดับเนื้อหาไว้

```text
สร้าง Web App เกม "คำใบ้ทายเพลงฮิต" เป็นแอปพลิเคชันหน้าเดียว (Single-page web app) ด้วย HTML, CSS และ JavaScript ไฟล์เดียว ไม่ต้องเชื่อมต่อฐานข้อมูลหลังบ้าน (No Backend) และไม่ต้องใช้ไลบรารีภายนอกที่ซับซ้อน (สามารถใช้ Tailwind CSS ผ่าน CDN ได้เพื่อความรวดเร็ว)

โครงสร้างข้อมูล (Data):
ให้สร้างตัวแปร Array of Objects ใน JavaScript เพื่อเก็บข้อมูลเพลงไทยฮิตจำนวน 150 เพลง (ในโค้ดเริ่มต้นนี้ ให้ mock up ข้อมูลตัวอย่างมาให้สมบูรณ์ก่อน 5 เพลง เพื่อให้ฉันนำไปเติมต่อเองได้) โดยแต่ละ Object ต้องมี properties ดังนี้:

title: ชื่อเพลง (คำตอบที่ถูกต้อง)
audio_url: ลิงก์ไฟล์เสียง (ใส่ URL จำลองเป็น placeholder ไว้ก่อน)
hint_1: คำใบ้จำนวนพยางค์ เช่น "ชื่อเพลงมี 2 พยางค์"

hint_2: คำใบ้ชื่อศิลปิน หรือ วงดนตรี

hint_3: คำใบ้ความหมายของเพลง หรือ เนื้อหาที่สื่อถึง

hint_4: คำใบ้ท่อนฮุค เช่น "ท่อนฮุคร้องว่า..."

กติกาและการทำงาน (State & Interactions):

เมื่อเริ่มเกม ให้สุ่มเพลงจาก Array ขึ้นมา 1 เพลง

บนหน้าจอจะมี "ป้ายคำใบ้ปริศนา" 4 ป้าย ซึ่งตอนแรกจะปิดอยู่ ผู้เล่นสามารถคลิกเพื่อเปิดดูคำใบ้ทีละป้ายได้ (มี State บันทึกว่าเปิดป้ายไหนไปแล้วบ้าง)

มีปุ่ม "ฟังเสียงเพลง" เมื่อกดจะเป็นการเล่นไฟล์เสียงจาก audio_url

มีช่อง Input Box ให้ผู้เล่นพิมพ์ทายชื่อเพลง และปุ่ม "ตอบ"

ระบบคะแนน: เริ่มต้นมี 100 คะแนน การเปิดป้ายคำใบ้ 1 ป้าย จะถูกหัก 10 คะแนน ถ้ากดปุ่มฟังเสียง หัก 20 คะแนน หากตอบถูก ให้แสดงข้อความยินดี สรุปคะแนนที่ได้ และมีปุ่มให้ "เล่นเพลงต่อไป"

หน้าตา (UI) และ สไตล์:

ออกแบบให้ดูสนุกสนาน ทันสมัย เหมือนรายการเกมโชว์ ใช้สีสันสดใส

แบ่ง Layout ชัดเจน: ด้านบนแสดงคะแนนปัจจุบัน ถัดมาเป็นปุ่มฟังเสียง พื้นที่ตรงกลางเป็น Grid 2x2 สำหรับป้ายคำใบ้ 4 ป้าย ด้านล่างเป็นช่องกรอกคำตอบและปุ่มยืนยัน

ต้องมีคำอธิบายวิธีเล่นสั้น ๆ อยู่ในหน้าเว็บด้วย เพื่อให้ผู้ใช้เข้าใจทันที

ข้อจำกัดทางเทคนิค:

ต้องรองรับการแสดงผลบนหน้าจอมือถือ (Responsive Design) ป้ายและปุ่มต่างๆ ต้องจัดเรียงใหม่ให้กดง่ายเมื่ออยู่บนจอมือถือ

ห้ามใช้ API ที่ต้องเสียเงิน หรือระบบล็อกอิน

มีการโต้ตอบกับผู้ใช้อย่างน้อย 3 อย่าง คือ กดเปิดป้ายคำใบ้, พิมพ์ข้อความเพื่อตอบ, และกดปุ่มเล่นเสียงดนตรี
```

## B.2 เหตุผลในการเขียน Prompt แบบนี้

| องค์ประกอบของ Prompt | เหตุผล |
| --- | --- |
| ระบุงานและผลลัพธ์ | กำหนดชื่อเกมและ single-page app เพื่อให้ AI ไม่สร้างระบบใหญ่เกินโจทย์ |
| กำหนดเทคโนโลยีและข้อจำกัด | HTML/CSS/JavaScript ไฟล์เดียว ไม่มี backend หรือบริการเสียเงิน ทำให้เปิดตรวจได้ง่าย |
| กำหนด schema | ระบุ title, audio_url และ hint_1–hint_4 ให้ข้อมูลและการแสดงผลสอดคล้องกัน |
| กำหนด state และกติกา | บอกวิธีสุ่มเพลง เปิดป้าย เล่นเสียง รับคำตอบ และหักคะแนน ช่วยลดการเดาพฤติกรรม |
| กำหนด UI และมือถือ | โครงคะแนน–เสียง–ป้าย–คำตอบ และสีแบบเกมโชว์ช่วยควบคุมหน้าตา |
| ให้เริ่มเพียง 5 เพลง | ลดขอบเขตต้นแบบและให้ตรวจกลไกเกมได้ก่อนจัดข้อมูลจำนวนมาก |

## B.3 ผลลัพธ์ที่ AI ให้ในครั้งแรก

ได้ไฟล์ index.html พร้อมเพลงตัวอย่าง 5 เพลง ได้แก่ ถ้าเราเจอกันอีก, คลั่งรัก, วาดไว้, โต๊ะริม และนะหน้าทอง มีป้ายคำใบ้ การสุ่มเพลง คะแนน ช่องพิมพ์คำตอบ การเฉลยเมื่อพิมพ์ถูก และปุ่มเล่นเพลงต่อไป หน้าตามีพื้นหลังเข้มและการ์ดสีสว่างแนวเกมโชว์

ส่วนที่ตรงกับ Prompt คือไฟล์เดียว โครงสร้างข้อมูล 5 เพลง ป้าย 4 ใบ คะแนนเริ่ม 100 และหน้าจอ Responsive ส่วนที่ยังไม่ใช่ผลลัพธ์ใช้งานจริงคือ audio_url ใช้ example.com ตามที่ Prompt อนุญาตไว้ เสียงจึงยังเล่นเพลงจริงไม่ได้ในต้นแบบ และคำใบ้บางรายการยังไม่ได้ตรวจความแม่นยำจากแหล่งข้อมูล

ต้นแบบหักคะแนนเมื่อกดฟังและเปิดป้าย แม้แหล่งเสียงเป็น placeholder จึงกลายเป็นประเด็นที่ต้องปรับในรอบต่อมา จากบทสนทนาช่วงแรกยังไม่มีหลักฐานการทดสอบเสียงผ่านเบราว์เซอร์จริงครบทุกเพลง

| 1<br>ปรับฟังก์ชันและข้อมูล | ต้องการให้เกมเล่นด้วยการเดาแล้วเปิดเฉลย เพิ่มประวัติ และเปลี่ยนจากข้อมูลตัวอย่าง 5 เพลงเป็น 150 เพลง | จากโค้ดเกม "คำใบ้ทายเพลงฮิต" เดิมที่เขียนด้วย HTML, CSS, JavaScript (Tailwind) หน้าเดียว ขอให้คุณปรับปรุงและแก้ไขโค้ดใหม่ตาม requirement ต่อไปนี้:<br><br>1. เปลี่ยนวิธีการตอบ (เปลี่ยนจาก Input เป็นปุ่มเฉลย):<br><br>ให้ลบช่อง Input Box สำหรับพิมพ์คำตอบ และปุ่ม "ส่งคำตอบ" ออกไป<br><br>แทนที่ด้วยปุ่ม "ดูเฉลยคำตอบ" (ดีไซน์ปุ่มให้ดูเด่นชัด)<br><br>เมื่อผู้เล่นกดปุ่ม "ดูเฉลยคำตอบ" ระบบจะจบเกมรอบนั้นทันที พร้อมซ่อนพื้นที่เล่น และแสดงหน้าต่างผลลัพธ์ (Result Area) โดยให้แสดงชื่อเพลงที่ถูกต้อง และบอก "คะแนนที่คุณทำได้ในรอบนี้" (คำนวณจากคะแนนที่เหลืออยู่หลังจากหักลบการเปิดป้ายและฟังเสียง)<br><br>2. เพิ่มระบบประวัติการเล่น (Play History):<br><br>สร้างตัวแปร State เป็น Array เพื่อเก็บประวัติการเล่น (เช่น playHistory)<br><br>ทุกครั้งที่กด "ดูเฉลยคำตอบ" หรือจบเกมในแต่ละรอบ ให้บันทึก "ชื่อเพลง" และ "คะแนนที่ได้ในรอบนั้น" ลงใน Array<br><br>เพิ่ม UI ในหน้าเว็บ (แนะนำให้อยู่ด้านล่างสุด ถัดจากส่วนการเล่น) เป็นหัวข้อ "ประวัติการเล่นของคุณ" ออกแบบเป็น List หรือ Table สวยๆ ด้วย Tailwind<br><br>UI ประวัติการเล่นนี้จะต้องอัปเดตอัตโนมัติทุกครั้งที่เล่นจบเพลง โดยแสดงรายการเพลงที่ผ่านมาแล้วเรียงจากล่าสุดไปเก่าสุด<br><br>3. เพิ่มฐานข้อมูลเพลงฮิต 150 เพลง:<br><br>ให้อัปเดตตัวแปร Array songs โดยสร้างข้อมูลเพลงไทยฮิต (คละยุคตั้งแต่ 90s, 2000s จนถึงยุคปัจจุบัน และคละแนวเพลง Pop, Rock, Indie) ให้ครบจำนวน 150 เพลง<br><br>แต่ละเพลงต้องมี properties โครงสร้างเหมือนเดิมทุกประการคือ: title, audio_url (ใช้ลิงก์จำลองได้), hint_1 (จำนวนพยางค์), hint_2 (ชื่อศิลปิน), hint_3 (ความหมาย/เนื้อหา), และ hint_4 (เนื้อเพลงท่อนฮุค) | สำเร็จด้าน UI/state; ข้อมูลและเสียงยังต้องแก้<br><br>เพิ่มปุ่มเฉลย พื้นที่ผลลัพธ์ และ playHistory เรียงล่าสุดก่อน ระบบซ่อนพื้นที่เล่นและเริ่มเพลงต่อไปได้ สร้างรายการต้นทาง 355 แถว ตัดชื่อซ้ำเหลือ 344 แล้วคัดตามตำแหน่งให้ songs มี 150 รายการ เสียงยังเป็น placeholder และคำใบ้ที่ 4 ใช้ข้อความที่แทรกชื่อเพลง จึงเปิดเผยคำตอบโดยตรง การตกแต่งยังใช้ CSS ที่เขียนเอง ไม่ได้เพิ่ม Tailwind | ข้อกำหนดที่แจกแจง state และผลเมื่อกดปุ่มช่วยให้ได้ฟังก์ชันชัดเจน แต่จำนวนรายการครบไม่ได้รับประกันคุณภาพข้อมูล ต้องตรวจคำใบ้ไม่ให้เฉลยทั้งชื่อ และตรวจเวอร์ชันเพลงแยกจากจำนวนเพลง |
| 2<br>แก้คำใบ้และขอแหล่งเสียงจริง | คำใบ้ที่ 4 เปิดชื่อเพลงและไม่เป็นเนื้อฮุคจริง ขณะที่ audio_url ยังเล่นไม่ได้ | แก้ไข คำใบ้ที่ 4 ให้เอาเนื้อเพลงจริงท่อนฮุคมาโดยห้ามบอกชื่อเพลงในคำใบ้ เช่นเพลง ซ่อนไม่หา คำใบ้ที่ 4 คือ ท่อนฮุคร้องว่า "ไม่ใช่เธอก็ไม่เป็นไรหรอกนะ ไม่ต้องทนอยู่เพื่อรอวันจากลา" เมื่อแก้ไขครบทุกเพลงแล้ว ให้ปรับ audio_url ให้สามารถกดฟังได้จริงทุกเพลง | ทำได้บางส่วน; ยังไม่ตรงเรื่องฮุคและเสียงในหน้า<br><br>ผู้ช่วยปฏิเสธการนำเนื้อร้องท่อนฮุคมาวางครบทุกเพลงโดยอ้างข้อจำกัดลิขสิทธิ์ แล้วใช้คำบรรยายแทนโดยไม่แทรกชื่อเพลง ส่วน audio_url เปลี่ยนเป็นลิงก์ค้นหา YouTube Music และใช้ window.open เปิดแท็บใหม่ จึงยังไม่ใช่เสียงที่เล่นภายในแอปตามเป้าหมาย | ตัวอย่างผลลัพธ์ช่วยระบุรูปแบบได้ดี แต่ต้องกำหนดแหล่งเนื้อหาที่ใช้ได้ และแยกคำว่า “ค้นหาเพลงได้” ออกจาก “เล่นเสียงในหน้าเว็บได้” ให้ชัด |
| 3<br>Debug การเล่นเสียงและคะแนน — แก้กลไกก่อนเติมข้อมูลจริง | ปุ่มฟังเปิดหน้าเว็บอื่น และมีการหักคะแนนจากการกดทั้งที่ไม่มีเสียงในเกม | แก้ไขให้แต่ละเพลงสามารถกดเล่นเสียงแล้วมีเพลงเล่นที่หน้า webapp นี้ได้เลย และเพลงที่ไม่สามารถเล่นได้ ใช้ขึ้นว่าไม่สามารถเล่นได้เนื่องจากติดลิขสิทธิ์ และไม่หักคะแนนสำหรับการกดคำใบ้เสียงในข้อนั้นๆ | แก้เงื่อนไขคะแนนแล้ว; เสียงยังไม่พร้อม<br><br>เพิ่มตัวเล่น HTMLAudioElement ภายในหน้า เปลี่ยนการหักคะแนนไปเกิดเมื่อได้รับ playing event และแสดงข้อความเมื่อไม่มีไฟล์หรือเล่นไม่ได้ แต่ผู้ช่วยกำหนด audio_url เป็น null ทุกเพลง เนื่องจากยังไม่ได้จัดหาไฟล์จริง ดังนั้นกลไกคะแนนได้รับการแก้แล้ว แต่การฟังเพลงทั้งชุดยังไม่สำเร็จในรอบนี้ | การแก้ event handler ไม่ทดแทนการมีแหล่งข้อมูลจริง เกณฑ์สำเร็จควรรวมทั้งเสียงที่ได้ยินและคะแนนที่เปลี่ยนถูกเวลา ห้ามรายงานว่าแก้เสียงสำเร็จเพียงเพราะมีแท็ก audio |
| 4<br>ย้ำรูปแบบคำใบ้ | คำใบ้ยังเป็นการบรรยายอารมณ์หรือความหมาย ผู้ใช้ต้องการเนื้อร้องตรง ๆ | แก้ไขคำใบ้ที่ 4 ให้เอาเนื้อร้องท่อนฮุคมามาตรงๆเลย ไม่ต้องสื่อหรือถ่อยทอดความรู้สึกของเพลง | ไม่เปลี่ยนโค้ด; ต้องเปลี่ยนแนวทาง<br><br>ผู้ช่วยปฏิเสธคำขอเนื้อร้องอีกครั้งและเสนอให้ใช้ข้อความที่มีสิทธิ์ใช้งานหรือคำใบ้เชิงข้อเท็จจริง ไม่มีการแก้ไฟล์ในรอบนี้ | การย้ำคำสั่งเดิมไม่ได้ช่วยเมื่ออุปสรรคคือข้อจำกัดของเนื้อหา ควรเปลี่ยนรูปแบบคำใบ้ให้ยังบรรลุเป้าหมายการทายเพลง |
| 5<br>ออกแบบคำใบ้ใหม่ด้วยตัวอย่างและกรณีพิเศษ | ต้องการคำใบ้ที่ชัดเจน ไม่ใช้เนื้อร้อง และไม่เฉลยชื่อเต็มสำหรับเพลงชื่อหนึ่งพยางค์ | แก้ไขคำใบ้ที่ 4 เป็น ในชื่อเพลง มีคำว่า... 1 พยางค์ เช่น เพลง ซ่อนไม่หา ใบ้ว่า ชื่อเพลงมีคำว่า "ซ่อน" แต่ถ้าชื่อเพลงมีชื่อ 1 พยางค์อยู่แล้ว ให้ใบ้นิยามเกี่ยวกับคำ1 พยางค์นั้นๆ เช่น เพลง ฟ้า ใบ้ว่า "ชื่อเพลงเป็นส่วนหนึ่งของชั้นบรรยากาศหรืออวกาศที่สามารถมองเห็นได้จากพื้นผิวโลก" | ได้รูปแบบใหม่; ข้อผิดพลาดการเฉลยถูกแก้ภายหลัง<br><br>เพิ่มรายการคำหนึ่งพยางค์และพจนานุกรมคำนิยาม แล้วเปลี่ยนป้ายเป็น “คำในชื่อเพลง” แต่โค้ด buildHint4 ขณะนั้นยังแทรกชื่อเต็มหน้าคำนิยามสำหรับเพลงชื่อหนึ่งพยางค์ จึงไม่ตรงข้อกำหนดทั้งหมด ข้อผิดพลาดนี้ถูกแก้ระหว่างการจัดข้อมูลชุดสุดท้าย และมีการตรวจว่า hint_4 ของชื่อหนึ่งพยางค์ไม่เปิดเผยชื่อเพลง | การให้ตัวอย่างปกติและกรณีพิเศษช่วยลดการเดา แต่ยังต้องตรวจผลจริงกับตัวอย่าง เช่น “ฟ้า” ต้องมีเฉพาะนิยาม ไม่มีคำเฉลยอยู่ด้านหน้า |
| 6<br>Debug ให้เล่นได้จริง + ตรวจข้อมูล + ขยาย 200 เพลง | ทุกเพลงยังมี audio_url เป็น null ข้อมูลปีและเวอร์ชันต้นฉบับยังไม่ชัดเจน และคำใบ้ชื่อหนึ่งพยางค์ยังมีจุดที่เปิดเผยคำตอบ | เพิ่มเนื้อหาในแต่ละข้อให้บอก ยุคและปีที่เพลงนั้นๆออก และ แก้ไขให้ทุกเพลงเป็นเพลง original ไม่ใช่ cover หรือมาทำใหม่ สามารถกดฟังเพลงได้ทุกเพลง จากแหล่ง itune catalog หรือแหล่งอื่นๆ ถ้าเพลงใดไม่สามารถนำมาได้จริงๆ ให้ติดเพลงนั้นออกและเอาเพลงอื่นมาทายเพลงแทน โดย เป็นเพลงฮิตที่ทุกคนรู้จักเพิ่มเป็น 200 เพลง | สำเร็จตามหลักฐานการทดสอบในเครื่อง; ยังไม่ได้ deploy<br><br>ดึงข้อมูล iTunes Search API ฝั่งประเทศไทย จับคู่ชื่อเพลงและศิลปิน คัดเวอร์ชันและรายการกำกวมออก แก้ปีบางรายการจากแหล่งอัลบั้มเดิม และสร้าง songs เป็นข้อมูล 200 รายการจริง มี URL เสียงตัวอย่างประมาณ 30 วินาทีทุกเพลง ทดสอบ Edge ถึง playing event ผ่าน 200/200 เพิ่มปี พ.ศ./ค.ศ. และยุคในรอบ ผลลัพธ์ และประวัติ เปลี่ยนเพลงเมื่อเสียงใช้ไม่ได้ หักคะแนนครั้งเดียวหลังเริ่มเล่น ป้องกัน callback เก่าหักคะแนนรอบใหม่ และแก้คำใบ้หนึ่งพยางค์ไม่ให้เฉลยชื่อ | Prompt ที่ระบุแหล่งข้อมูล เกณฑ์คัดออก และนิยามความสำเร็จที่ทดสอบได้ช่วยปิดงานได้จริง ต้องตรวจทั้งจำนวน ความถูกต้องของเวอร์ชัน การเข้าถึงไฟล์ และการเล่นผ่านเบราว์เซอร์ |
| 7<br>แก้คำใบ้ที่ 4 ซึ่งเป็นตัวอักษรกลางคำ | บางเพลงใช้ชุดตัวอักษรที่อยู่ในชื่อเพลง แต่ไม่ได้เป็นคำที่อ่านได้ตามความหมาย เช่น “เพลงสุดท้าย” ใบ้ว่า “ลง” เพราะตัวอักษรนี้อยู่ท้ายคำว่า “เพลง” | แก้ไขคำใบ้ที่ 4 มีจุดบกพร่อง เช่นเพลง "เพลงสุดท้าย" คำใบ้เป็นคำว่า "ลง" ทั้งที่ควรเป็นคำว่า "เพลง" | แก้แล้ว 10 เพลงใน `index.html` โดยเปลี่ยนเฉพาะ `hint_4` ให้เป็นคำในชื่อเพลงที่สื่อความหมายจริง เช่น “เพลงสุดท้าย” และ “เพลงนี้เกี่ยวกับความรัก” ใช้ “เพลง”; “อยากร้องดังดัง” ใช้ “ร้อง” ตรวจข้อมูลเพลงครบ 200 รายการและตรวจคำใบ้ที่แก้ทั้ง 10 รายการผ่าน ไม่ได้ทดสอบการเล่นเสียงซ้ำในรอบนี้ | การตรวจเพียงว่าข้อความใบ้เป็น substring ของชื่อเพลงยังไม่พอ ต้องตรวจขอบเขตคำและความหมายของคำด้วย โดยเฉพาะภาษาไทยที่เขียนคำติดกัน |

# ส่วน C — หลักฐานกรณี Debug

## C.1 ปุ่มฟังเพลงมีอยู่ แต่ไม่มีเพลงเล่นในหน้าเว็บ

ลำดับปัญหาเริ่มจาก URL จำลอง ต่อมาเปลี่ยนเป็นลิงก์ค้นหา YouTube Music ซึ่งเปิดแท็บใหม่ และจากนั้นเปลี่ยนมาใช้ audio_url: null ทุกเพลง แม้มีตัวเล่นภายในหน้าแล้วก็ตาม ผู้ใช้จึงสั่งชัดเจนในรอบ 3 ว่าต้องได้ยินเสียงในเว็บและห้ามหักคะแนนหากเล่นไม่ได้ ก่อนเพิ่มเงื่อนไขหาเพลงทดแทนและทดสอบทุกเพลงในรอบ 6

| จุดตรวจ | หลักฐานและความหมาย |
| --- | --- |
| สาเหตุด้านข้อมูล | example.com เป็น placeholder; ลิงก์ค้นหา YouTube Music เป็นหน้าเว็บ ไม่ใช่ไฟล์เสียง; null ไม่มีสื่อให้เล่น |
| สาเหตุด้าน event | การหักคะแนนตอน click ไม่ยืนยันว่าเสียงเริ่มเล่น และ callback เก่าอาจกระทบรอบใหม่ |
| การแก้ข้อมูลรอบสุดท้าย | จัดหา URL preview ที่ตอบเป็นสื่อจริงจากแค็ตตาล็อก และแทนที่ข้อมูลด้วย 200 รายการที่ผ่านเกณฑ์ |
| การแก้ state | หักคะแนนใน onplaying ครั้งเดียว ใช้ audioCharged และ audioGeneration พร้อมยกเลิกการเล่นเมื่อเปลี่ยนรอบ |

## C.2 ตัวอย่างโค้ดแกนสำคัญในเวอร์ชันปัจจุบัน

# ส่วน D — สรุปสิ่งที่ได้เรียนรู้

ข้อความส่วนนี้เป็นร่างสะท้อนการเรียนรู้ที่สังเคราะห์จากบทสนทนา นักศึกษาควรอ่านและปรับถ้อยคำให้ตรงกับสิ่งที่ตนเองคิดและลงมือทำจริงก่อนส่ง

## 1. Prompt แบบไหนได้ผลดี และแบบไหนเสียเวลา

Prompt ที่ได้ผลดีกับงานนี้คือการระบุบริบท เทคโนโลยี กติกา state และผลเมื่อกดปุ่มอย่างเจาะจง ตัวอย่างคือคำสั่งเพิ่ม playHistory ที่บอกทั้งข้อมูลที่จะเก็บ จังหวะบันทึก และการเรียงล่าสุดก่อน อีกตัวอย่างคือคำใบ้ชื่อหนึ่งพยางค์ที่ให้กรณี “ซ่อน” กับ “ฟ้า” ทำให้เห็นทั้งกรณีปกติและข้อยกเว้น ส่วนที่เสียเวลาคือการย้ำให้ใช้เนื้อร้องตรง ๆ โดยยังไม่เปลี่ยนวิธีแก้ข้อจำกัดของเนื้อหา และการขอให้เพลงเล่นได้โดยไม่ระบุว่าต้องเป็นไฟล์เสียงตรงและผ่านการทดสอบจริง

## 2. AI เขียนผิดหรือมั่วตรงไหน และรู้ได้อย่างไร

AI เคยใส่ชื่อเพลงลงในคำใบ้ที่ไม่ควรเฉลย รวมถึงกรณีชื่อหนึ่งพยางค์ อีกทั้งเคยให้ลิงก์ค้นหาเพลงแทนลิงก์ไฟล์เสียง และต่อมาตั้ง audio_url เป็น null ทุกเพลง จึงยังไม่มีเสียงจริงแม้หน้าตาปุ่มดูพร้อม ข้อมูลปีจากแค็ตตาล็อกบางรายการก็ไม่ตรงปีออกครั้งแรก การรู้ว่าแก้สำเร็จต้องอาศัยทั้งการอ่านโค้ด ตรวจแหล่งข้อมูล และหลักฐานเล่นเสียง 200/200 ไม่ใช่เชื่อเพียงข้อความสรุปของ AI

## 3. ถ้าย้อนกลับไปเขียน Prompt แรกใหม่ จะเขียนอย่างไร

จะระบุรูปแบบเกมสุดท้ายตั้งแต่ต้นว่าเดาในใจแล้วเปิดเฉลย กำหนดคำใบ้แบบไม่ใช้เนื้อร้อง ใส่ปีและแหล่งอ้างอิงทุกเพลง และบอกให้เลือกแหล่งเสียงที่ใช้กับรูปแบบแอปได้ กำหนดเกณฑ์ว่าไฟล์ต้องเริ่มเล่นจริงก่อนหักคะแนน ถ้าเล่นไม่ได้ต้องมีเพลงทดแทน และห้ามรายงานว่าทำสำเร็จเมื่อยังเป็น placeholder พร้อมแยกเกณฑ์ทดสอบการทำงานออกจากความสวยงาม ตัวอย่าง Prompt ที่ปรับปรุงอยู่ในภาคผนวก

## 4. งานนี้เปลี่ยนมุมมองต่อการใช้ AI เขียนโค้ดอย่างไร

AI ช่วยสร้างต้นแบบและแก้ UI ได้รวดเร็ว แต่ผู้ใช้ยังต้องเป็นคนกำหนดนิยามความสำเร็จและตรวจผล งานที่ดูเสร็จอาจยังขาดข้อมูลจริงหรือมี state ที่ผิด การพัฒนาจึงเป็นวงจรกำหนดสิ่งที่ต้องการ ตรวจสิ่งที่ได้ แล้วปรับคำสั่งจากหลักฐาน ขณะเดียวกันต้องแยกความสามารถทางเทคนิคออกจากสิทธิ์การใช้เนื้อหา การเล่นพรีวิวได้ไม่ได้ยืนยันว่านำไปเผยแพร่เป็นเกมได้ทุกกรณี และต้องยอมรับสิ่งที่ยังไม่ทดสอบ เช่น การ deploy และการใช้งานบนมือถือจริง

## 1.4 กติกาคะแนนและจุดสิ้นสุดรอบ

คะแนน = max(0, 100 − 10 × จำนวนป้ายที่เปิด − 20 × สถานะการฟังสำเร็จครั้งแรก) โดยสถานะการฟังสำเร็จมีค่า 0 หรือ 1 ในรอบปกติคะแนนต่ำสุดจึงเป็น 40 หลังเปิดครบ 4 ป้ายและฟังเสียงสำเร็จ ข้อความคะแนน 100–0 ในการ clamp เป็นการป้องกันค่าติดลบ ไม่ใช่ว่ากติกาปัจจุบันทำให้ลดลงถึง 0 ได้ตามปกติ

การกดดูเฉลยจะจบรอบเสมอ หยุดเสียง ซ่อนพื้นที่เล่น และเพิ่มประวัติหนึ่งรายการ ปุ่มเล่นเพลงต่อไปเพิ่มเลขรอบและคืนคะแนนเป็น 100 การคลิกซ้ำหลังจบรอบถูกกันไม่ให้เพิ่มประวัติซ้ำ

## 1.5 กรณีเสียงไม่พร้อม

หากเบราว์เซอร์บล็อก autoplay หรืออุปกรณ์ออฟไลน์ แอปแสดงให้ลองใหม่โดยไม่หักเพิ่ม หากเป็นความล้มเหลวของสื่อ/รอเกินเวลาจะกันเพลงนั้นออกจากชุด แล้วเปลี่ยนเป็นเพลงใหม่ที่ 100 คะแนน ป้ายเดิมถูกปิดใหม่และไม่มีการเพิ่มประวัติรอบที่เสีย หากกันเพลงออกครบชุดจะมีปุ่มลองโหลดเพลงใหม่

ประวัติและรายชื่อเพลงที่ถูกกันออกอยู่ในหน่วยความจำของหน้าเว็บเท่านั้น การรีเฟรชหน้าจะเริ่ม state ใหม่ ไม่มี localStorage หรือฐานข้อมูลถาวร

## 2.2 วิธีคัดเลือก

ผู้ช่วยค้นข้อมูลเพลงของศิลปินผ่าน iTunes Search API โดยระบุ country=th จับคู่ชื่อและศิลปิน กรองคำบอกเวอร์ชัน เช่น cover, live, remix, remaster, acoustic และตัดอัลบั้มรวม/รายการที่กำกวมหลายรายการออก เลือกแหล่งอัลบั้มสตูดิโอหรือซิงเกิล และใช้ข้อมูลอ้างอิงเสริมเมื่อพบว่าปีของแค็ตตาล็อกคลาดจากปีเผยแพร่เดิม

ตรวจลิงก์สื่อของผู้สมัคร 214 รายการด้วย HTTP HEAD และชนิดไฟล์ จากนั้นคัดเหลือ 200 รายการสำหรับแอป การตรวจเบราว์เซอร์รอ playing event ผ่านครบ 200 รายการ พรีวิวยาวประมาณ 29.98–30.02 วินาที ไม่มีการฝังไฟล์เพลงเต็มหรือดาวน์โหลดไฟล์เสียงมาเก็บในเว็บแอป

## 2.4 ข้อจำกัดที่ต้องแจ้งตามจริง

- คำว่า “original” ในชุดนี้อาศัยการจับคู่ศิลปิน/ชื่อ/อัลบั้มและกรองเวอร์ชันจากข้อมูลผู้เผยแพร่ ไม่ใช่ใบรับรองสิทธิ์หรือการตรวจประวัติ master recording อย่างอิสระทุกเพลง

- ปีเพลงมี source_url และ year_source ให้ตรวจย้อนกลับ บางเพลงมีปีซิงเกิลและปีอัลบั้มต่างกัน และ metadata ของผู้ให้บริการอาจเปลี่ยน

- พรีวิวเป็นเพียงคลิปประมาณ 30 วินาที การตอบกลับสำเร็จและการเริ่มเล่นวันนี้ไม่รับประกันว่า URL จะใช้ได้ตลอดไปหรือทุกเครือข่าย

- ไม่มีหลักฐานรับรองว่าเพลงทั้ง 200 เป็นเพลงที่ “ทุกคน” รู้จัก ความคุ้นเคยขึ้นกับวัยและแนวเพลงของผู้เล่น

- เงื่อนไข iTunes จำกัดพรีวิวไว้เพื่อโปรโมตเนื้อหาที่เกี่ยวข้อง การนำไปเผยแพร่เป็นเกมอิสระต้องพิจารณาเงื่อนไขและสิทธิ์ก่อน แม้ไฟล์จะเล่นได้ทางเทคนิค

- ระหว่างจัดทำโครงการ ระบบอัตโนมัติปฏิเสธคำสั่งลบ .catalog-work แบบ recursive จึงยังมีโฟลเดอร์งานชั่วคราวอยู่ โดยไม่จำเป็นต่อการเปิด index.html

# ภาคผนวก 5 — ตัวอย่าง Prompt ที่ปรับปรุงและคำขอจัดทำรายงาน

Prompt ต่อไปนี้เขียนขึ้นภายหลังเพื่อสะท้อนบทเรียน ไม่ใช่ข้อความที่ใช้จริงในรอบพัฒนาที่ผ่านมา จึงไม่นับเป็นรอบ iterate เพิ่ม

```text
สร้างเว็บแอปหน้าเดียวชื่อ “คำใบ้ทายเพลงฮิต” ด้วย HTML, CSS และ JavaScript ใน index.html ไฟล์เดียว ใช้ได้บนคอมพิวเตอร์และมือถือ ไม่ใช้ backend, login, API key หรือบริการเสียเงิน

ผู้ใช้เดาชื่อเพลงในใจแล้วกดดูเฉลย ไม่ต้องมีช่องพิมพ์คำตอบ มีคำใบ้ 4 ป้าย: จำนวนพยางค์, ศิลปินต้นฉบับ, ความหมายเพลง และคำหนึ่งพยางค์จากชื่อเพลง หากชื่อเพลงมีเพียงหนึ่งพยางค์ให้ใช้นิยามโดยห้ามแสดงชื่อเพลง เช่น “ฟ้า” ให้บรรยายสิ่งที่มองเห็นเหนือพื้นโลก

ใช้ข้อมูลเพลงไทยฮิต 200 เพลง ตั้งแต่ยุค 90s ถึงยุค 2020s คัดเวอร์ชันต้นฉบับจากข้อมูลศิลปินและอัลบั้ม พร้อม release_year, era, source_url และ year_source แยกปีออกครั้งแรกจากปีออกซ้ำ ห้ามสร้างปีหรือ URL เสียงขึ้นเอง แสดงยุคและปี พ.ศ./ค.ศ. ในแต่ละรอบ

ต้องมีตัวอย่างเสียงที่ได้รับอนุญาตให้ใช้ตามรูปแบบแอป เล่นได้ภายในหน้า ถ้าแหล่งที่เสนอมีข้อจำกัดให้รายงานก่อนอ้างว่าใช้ได้ ทุก URL ต้องตรวจทั้งการตอบกลับและการเริ่มเล่นจริงในเบราว์เซอร์ ตัดเพลงที่ยืนยันเสียงหรือเวอร์ชันไม่ได้ออกและแทนด้วยเพลงอื่นให้ครบ 200

เริ่มรอบละ 100 คะแนน เปิดคำใบ้ใหม่หัก 10 คะแนนครั้งเดียว ฟังเสียงหัก 20 คะแนนเฉพาะเมื่อเริ่มเล่นสำเร็จ ฟังซ้ำหรือฟังต่อไม่หักเพิ่ม ถ้าเสียงใช้ไม่ได้ให้ข้ามเพลงนั้นและเริ่มรอบทดแทนที่ 100 คะแนน โดยไม่บันทึกคะแนนรอบที่เสีย แยกปัญหาเครือข่ายกับการถูกจำกัดสิทธิ์ ไม่สรุปสาเหตุลิขสิทธิ์จาก error ทุกชนิด

เมื่อกดเฉลย ให้หยุดเสียง ซ่อนพื้นที่เล่น แสดงชื่อเพลง ศิลปิน ปี คะแนน และปุ่มเล่นต่อ บันทึกลง playHistory เรียงล่าสุดก่อน สุ่มแบบไม่ซ้ำจนหมดชุด ป้องกัน event ของเพลงก่อนหน้ามาเปลี่ยนคะแนนรอบใหม่

ออกแบบแนวเกมโชว์สีสดใส มีคำอธิบายวิธีเล่นและปุ่มกดง่ายบนมือถือ ส่งไฟล์พร้อมรายงานตรวจจำนวนเพลง แหล่งข้อมูล การเล่นเสียง คะแนน การเปลี่ยนรอบ ประวัติ และหน้าจอมือถือ ระบุสิ่งที่ยังไม่ผ่านหรือยังไม่ได้ deploy ตามจริง
```
